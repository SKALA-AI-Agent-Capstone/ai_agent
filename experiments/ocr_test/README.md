# OCR 방식 비교 실험 (ocr_test 브랜치 전용, main에 합치지 않음)

광고 이미지를 내용 구간으로 자른 뒤, 구간마다 글자와 [이미지] 묘사를 두 방식으로 뽑아 나란히 비교한다.
서비스 코드는 건드리지 않고 `capstone_shared.documents`의 `tile_image`(구간 분할)와 `local_ocr`(Tesseract)만 가져다 쓴다.

## 실행

```sh
sh experiments/ocr_test/run.sh      # http://127.0.0.1:8090 에서 이미지를 올리고 '분석'
```

- 호스트에 Tesseract가 없어도 되게 기존 Python 이미지(`beauty-capstone-python:dev`, 한국어 Tesseract 포함)에서 돈다.
- 키는 `../backend/.env`에서 컨테이너 환경으로만 넘긴다. 다른 env 파일은 `ENV_FILE=...`로 지정한다.
- 모델은 env의 `VISION_MODEL`, `TEXT_MODEL`(기본 gpt-5.4-mini)을 쓴다.

## 두 방식

| | 1번: OCR 정리 + 비전 합치기 | 2번: OCR 위치 + 비전 판독 |
| --- | --- | --- |
| OCR | Tesseract가 읽은 줄을 텍스트 모델이 정리(띄어쓰기, 깨진 글자). 이미지는 안 봄 | Tesseract는 글자 위치(줄 상자)만 제공 |
| 비전 | 원본을 직접 읽고, 정리된 OCR 줄을 참고로 받아 합침(중복 제외). OCR 덕분에 찾은 글자는 `source=ocr` | 원본과 번호 상자 그림을 함께 받아 상자마다 글자를 읽고, 상자 밖 글자와 [이미지]를 묘사 |
| 모델 호출 | 구간당 2회(OCR 줄이 없으면 1회) | 구간당 1회 |
| 출력 | 글자 덩어리(따옴표 단위), [이미지] 사실 묘사 | 같음 + 덩어리마다 상자 번호(위치) |

## 2026-10-22 첫 실행 (투집 포어본드 광고 2장)

| 이미지 | 1번 | 2번 |
| --- | --- | --- |
| 06.jpg (848x2412, 2구간) | 호출 3, 입력 3,815 / 출력 683토큰, 8.7초 | 호출 2, 입력 6,147 / 출력 453토큰, 6.4초 |
| 상세페이지 (780x2324, 3구간) | 호출 6, 입력 4,653 / 출력 1,175토큰, 14.5초 | 호출 3, 입력 6,648 / 출력 741토큰, 10.0초 |

구간은 병렬로 처리해 이미지 한 장 전체는 약 6초였다.

### 둘 다 기존 파이프라인보다 나아진 점
- 기존 결과의 대표 오류가 사라졌다.
  - 카드 세 장 제목이 한 줄로 합쳐지던 것("인체 적용 시험 완료 POREBOND™ 2t¢ 모공 특허 듀얼 배합") → 카드별로 분리되어 읽힘
  - "함유"가 "2t¢"로 읽히던 것 → "10,000PPM 함유"로 정확히 읽힘
  - "2주"가 "주"로 빠지던 것 → "2주 안에 개선하는 신개념 모공 케어"로 정확히 읽힘
- 띄어쓰기가 깨진 줄("모공 크 기 와 개 수 가")은 두 방식 모두 바르게 나왔다.

### 차이
- **묶음**
  - 1번은 카드 단위로 자연스럽게 묶었다('01' 'POINT' '인체적용시험 완료' 한 덩어리).
  - 2번은 OCR 상자를 따라 더 잘게 나뉘었다('01' 'POINT'와 '인체적용시험 완료'가 별도). 한국어와 영어 번역 줄도 따로 나뉨.
- **위치**: 2번은 덩어리마다 상자 번호가 붙어 화면 박스를 그릴 수 있을 것처럼 보이지만, **모델이 붙인 상자 번호를 그대로 믿으면 안 된다.**
  - 상세페이지 3구간에서 "POREBOND™ 함유"를 상자 11로, "모공 특허 듀얼배합"을 상자 14로 붙였다. 둘 다 실제로는 세 카드 제목이 한 줄로 잡힌 상자 7의 일부였다.
  - 그 뒤 번호도 하나씩 밀렸다.
  - 위치는 모델 번호 대신, 읽은 글자를 OCR 상자 글자와 코드로 맞춰서 정해야 한다. 1번도 같은 방법으로 위치를 붙일 수 있다.
- **OCR이 아무것도 못 찾은 구간**: 06.jpg 첫 구간(큰 회색 제목)에서 Tesseract가 0줄을 냈다.
  - 2번은 그때 순수 비전 판독이 된다.
  - 모델이 없는 상자 번호(1~7)를 지어내는 현상이 있어, 코드에서 실제 상자 번호만 남기도록 고쳤다.
- **비용, 속도**: 2번이 호출 수와 시간이 적다. 이미지를 두 장(원본, 상자 그림) 보내서 입력 토큰은 더 많다.

### 둘 다 남은 문제
- **작은 각주 오독**: "*투집 포어본드 일시적 모공..." 각주의 "투집"을 1번은 "튜집", 2번은 "트집"으로 읽었다.
  - 작은 글자는 해당 상자만 확대해 다시 읽는 단계가 필요하다(설계의 '확대 재판독').
- **장식 글꼴 로고**: 첫 구간의 "TUJIB" 로고를 둘 다 "TOJIB"로 읽었다.
- **글자 배치 묘사**: [이미지] 묘사에 "세 줄의 글자가 배치되어 있음"처럼 글자 배치를 쓰는 경우가 있다. 2번이 더 자주 그런다. 프롬프트를 더 좁혀야 한다.
- **1번의 출처 표시**: 1번이 거의 모든 덩어리를 `source=ocr`로 표시한 구간이 있어, 이 표시는 믿기 어렵다.

## 3번 추가 (2026-10-22): 의미 덩어리 + 코드 대조

2번 구조에 의미 덩어리 묶기와 그래프, 피부, 제형 중심 이미지 묘사를 얹고, 덩어리를 코드가 OCR 줄과 대조한다.
`OCR 확인`, `숫자 불일치`, `비전만` 상태는 모델 자기신고가 아니라 코드가 계산한다. 페이지는 1, 2, 3번을 한 번에 비교한다.

검사.jpg(17구간) 실행: 1번 호출 28, 토큰 약 37,800 / 2번 호출 17, 토큰 약 55,200 / 3번 호출 17, 토큰 약 58,600. 구간은 병렬이라 이미지 한 장 약 41초.

- 잘 된 점: 그래프 행(큰 수치, 라벨, 평가 방법, 사용 전/후)이 한 덩어리로 묶이고 반복 라벨은 labels로 접혔다. "(피부노화지수 평가)"도 정확히 읽혔다(1회 실행에서는 "피부보화지수"로 흔들림).
- 남은 문제: 숫자 불일치 표시가 오탐일 수 있다. OCR 쪽이 숫자를 틀리게 읽은 경우(예: 8.51%)에도 비전 쪽에 경고가 붙는다. 이미지 묘사에 가끔 패널 배치나 캡션 글자가 섞인다.

### 3번 조정: 광고 문구만 (2026-10-22)
- 제품 표면에 인쇄된 글자(용기, 라벨, 포장)는 광고 글자에서 빼고 `on_product_text`에만 따로 적는다. 무엇을 뺐는지 화면에서 확인하게 하려는 것이다.
  - 구분 기준: 사진 속 사물 위에 인쇄된 글자는 제품 표면 글자, 광고 제작자가 이미지 위에 얹은 글자는 광고 문구.
  - 검사.jpg 구간 1: 용기 글자('Pyunkang Yul', 'Red Ginseng Propolis Repairing Moisturizer', '30 ml / 1.01 Fl. oz.' 등)가 제외되고 광고 문구만 남았다.
- role에서 product를 없앴다(claim, condition, result만).
- 뒤 단계로 넘기는 것(`forward`)은 광고 문구(역할, 글자, 묶음 이름, 읽기 신뢰도)와 시각 묘사뿐이다. 상자 좌표, OCR 원문, 제품 표면 글자는 넘기지 않는다.
- 남은 문제: 제품명이 광고 제목으로 들어간 경우("편강율 레드 진생 프로폴리스 리페어링 크림")는 광고 문구로 남는다. 한 덩어리에 수치와 홍보 문구가 섞이는 경우가 있다("20층 보습", "20.48% 개선", "속부터 탄탄하게 보습 리프팅").

### 이미지 묘사 제거 (2026-10-22)
이미지 내용은 쓰지 않기로 해서 세 방식 모두 글자만 읽는다. 광고 문구만 읽고 제품 표면 글자는 `on_product_text`로 따로 빼는 규칙을 1, 2번에도 똑같이 적용해 같은 조건으로 비교한다.
검사.jpg(17구간): 1번 호출 28, 토큰 약 37,700 / 2번 호출 17, 토큰 약 55,300 / 3번 호출 17, 토큰 약 57,400. 이미지 한 장 약 34초(묘사 제거 전 41초).
- 구간 1에서 2번은 광고 문구를 거의 못 읽고 `[판독 불가]`만 냈다. 상자가 많고 글자가 큰 장식 영역에서 상자 위치 읽기가 무너진 것으로 보인다. 1번과 3번은 같은 구간을 읽어 냈다.
- 구간 9의 "(피부노화지수 평가)"는 3번만 정확했고 1번은 "피부 노화지수", 2번은 "피부보화자수"로 읽었다.

### 제품 표면 글자 제외 강화 (2026-10-22)
용기 라벨 글자('Pyunkang Yul' 등)가 광고 문구 덩어리로 섞여 나오는 문제가 있었다(3번 구간 10).
- 프롬프트: 제품 표면 글자의 특징(곡면을 따라 기울거나 휘고, 작고, 상표, 제품명, 영문 설명, 용량)을 알려 주고, 글자를 쓰기 전에 제품 표면 글자를 먼저 `on_product_text`에 쓰게 했다. 출력 스키마에서도 `on_product_text`를 맨 앞에 두었다.
- 코드: 모델이 제외 목록에 쓰고도 광고 문구에 다시 쓴 글자는 코드가 지운다.
- 결과(검사.jpg 17구간): 광고 문구에 남은 라벨 글자 수가 1번 0, 2번 0, 3번 0(이전 3번은 5). 스키마 순서를 바꾸기 전에는 3번 구간 10에서 모델이 제외 목록을 비워 둔 채 라벨 글자를 광고 문구로 썼다.
- 한계: 영문 상표처럼 눈에 띄는 라벨만 확인했다. 제품 위의 한글 광고 문구와 라벨 글자 경계가 애매한 경우는 더 봐야 한다.
